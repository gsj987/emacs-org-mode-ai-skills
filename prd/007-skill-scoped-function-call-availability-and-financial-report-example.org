#+TITLE: PRD 007 - Skill-Scoped Function Call Availability and Financial Report Example
#+STARTUP: overview

* Problem
Current skill specs can declare function calls in metadata, but there is no runtime
guarantee that callable functions are available only when a skill is actively applied.
This can blur spec-vs-run boundaries and expose functions outside intended scope.

We need a mechanism where functions declared by a skill are loaded/available only
for gptel requests while that skill is fully applied, and unloaded/unavailable when
the skill is excluded.

We also need one concrete example skill that demonstrates this flow end-to-end:
fetch financial news via Search1API and produce a daily Org report.

* Scope
- In scope:
  - Define and implement skill-scoped function registration lifecycle:
    - On skill apply: declared functions become available for gptel request context.
    - On skill exclude/unapply: those functions are removed from active availability.
  - Add an explicit runtime contract for "fully applied" skill state before functions
    are exposed.
  - Add one example skill spec file under =skills/= that declares a financial-news
    reporting function.
  - Implement one corresponding Elisp function in =elisp/= that calls Search1API and
    returns/produces Org-ready daily financial report content.
  - Ensure gptel request construction reflects only currently available function calls.
  - Add tests for apply/exclude lifecycle and failure scenarios.
  - Update README usage/docs for skill-scoped function availability and the new example.
  - Revise architecture so skill-specific Elisp functions are defined in skill org files
    (code blocks) instead of core =elisp/org-ai-skills.el=.
  - Load skill-defined functions as read-only spec-derived runtime state only when a skill
    is applied, and unload them when excluded.
- Out of scope:
  - Building a generic plugin/package manager for arbitrary external tools.
  - Persisting long-term function registry state across Emacs restarts.
  - Expanding to non-financial data sources beyond the Search1API example.

* Constraints
- Technical constraints:
  - Preserve spec vs run separation:
    - Skill spec files remain static.
    - Runtime function availability is derived state, not spec mutation.
  - No global side effects beyond explicit runtime registry changes.
  - Skill exclusion must reliably remove function availability for subsequent requests.
  - Search1API integration must have clear error handling for missing credentials,
    HTTP failures, and malformed responses.
  - Credentials must be loaded via auth-source using:
    =(auth-source-pick-first-password :host "search1api")=
    with no hardcoded API keys.
  - Org report output should be deterministic in structure (even if news content varies).
  - Skill-specific function implementation must be co-located in the skill file as code blocks.
  - Core runtime should not contain Search1API business functions for example skill behavior.
- Process constraints:
  - Follow AGENTS workflow: PRD -> implementation -> tests -> test run -> README -> worklog.
  - Do not implement code before PRD review/approval.

* Expected Behavior
- Behavior 1:
  - Parsing a skill with =Function Calls= declarations does not by itself expose
    executable functions globally.
- Behavior 2:
  - When a skill is fully applied in runtime flow, only that skill's declared
    functions become available to gptel request/tool context.
- Behavior 3:
  - If a skill is excluded/unapplied, its functions are no longer available in
    subsequent gptel requests.
- Behavior 4:
  - Example financial-news skill can invoke a Search1API-backed Elisp function and
    produce an Org-mode daily report structure.
- Behavior 5:
  - Missing Search1API configuration or API failure returns explicit, testable error
    behavior without silent fallback.
  - API key lookup must come from auth-source host =search1api=.
- Behavior 6:
  - Example skill remains a single packaged artifact: function declarations and Elisp
    function definitions are both inside one skill org file.
