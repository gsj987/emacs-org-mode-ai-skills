#+TITLE: PRD 010 - Role-Scoped gptel Model and System Prompt Configuration
#+STARTUP: overview

* Problem
Current `org-ai-skills` dispatch uses the active/default gptel configuration for all requests.
That means planner and execution calls share the same model and do not enforce a stable system instruction contract.

This causes two concrete issues:
- Planner output quality/format can drift because no dedicated planner role prompt is fixed.
- Skill execution can ignore scope/format constraints (especially strict Org output shape) when system-level guardrails are not fixed.

We need explicit, role-scoped controls so:
- Planner requests use planner-specific model + system prompt.
- Skill execution requests use execution-specific model + system prompt.

* Scope
- In scope:
  - Add user-configurable role-scoped model selection for:
    - planner requests
    - execution/rewrite requests
  - Add fixed default system prompts for:
    - planner role
    - execution role
  - Ensure dispatch applies role-scoped model/system values per request.
  - Keep prompt composition explicit and testable.
  - Add ERT tests for role routing, fallback behavior, and prompt contract attachment.
  - Update README usage/configuration docs.
- Out of scope:
  - Per-skill model overrides in MVP.
  - Dynamic runtime prompt editing UI in MVP.
  - Provider-specific advanced routing policies (latency/cost aware) in MVP.

* Constraints
- Technical constraints:
  - Preserve backward compatibility for users who do not set custom model/system values.
  - Planner must still return strict machine-parseable JSON contract.
  - Execution must still return artifact-only Org content, no prose chatter.
  - No mutation of skill spec files; runtime config only.
  - Integrate through existing `gptel-request` path with minimal coupling to provider internals.
- Process constraints:
  - Follow AGENTS workflow: PRD -> implementation -> tests -> test run -> README -> worklog.

* Expected Behavior
- Behavior 1:
  - Planner dispatch uses planner model setting (or fallback) and planner system prompt.
- Behavior 2:
  - Step execution/rewrite dispatch uses execution model setting (or fallback) and execution system prompt.
- Behavior 3:
  - Manual single-skill rewrite flow and autonomous planner flow both honor role-scoped config.
- Behavior 4:
  - Debug logs include effective role/model/system routing metadata per request.
- Behavior 5:
  - If role-specific model is nil/unset, dispatch cleanly falls back to gptel default model.

* Spec Design
** 1) Role Definition
Introduce explicit request roles in runtime payload:
- `planner`
- `execution` (covers manual rewrite and planner step execution dispatches)

Each outbound request carries `:request-role` for deterministic routing and observability.

** 2) New User Configuration (proposed)
Add defcustoms:
- `org-ai-skills-model-planner`
  - Type: nullable symbol/string (aligned with gptel model conventions)
  - Default: nil (fallback to gptel default model)
- `org-ai-skills-model-execution`
  - Type: nullable symbol/string
  - Default: nil
- `org-ai-skills-system-prompt-planner`
  - Type: string
  - Default: stable planner system prompt template (see section 3)
- `org-ai-skills-system-prompt-execution`
  - Type: string
  - Default: stable execution system prompt template (see section 4)

Optional future extension (not MVP):
- generic alist-based router: role -> model/prompt tuple.

** 3) Planner System Prompt (Default Template)
Goal: constrain planner to planning only, strict JSON, no hidden reasoning output.

Proposed baseline semantics:
- You are the planner for `org-ai-skills`.
- Task: select skill candidates and produce an executable plan only.
- Use only supplied metadata and run-state context.
- Output must be strict JSON object with required keys.
- No markdown, no explanations, no chain-of-thought, no extra keys.
- Respect runtime limits (`max_steps`, `max_skills_per_step`, batching mode context).

Prompt-quality guardrails:
- Explicitly reject narrative output.
- Explicitly forbid unsupported skill ids.
- Encourage short deterministic `why` fields (concise, auditable).

** 4) Execution System Prompt (Default Template)
Goal: enforce scope fidelity + Org artifact output contract.

Proposed baseline semantics:
- You are executing an `org-ai-skills` plan step in bounded scope.
- Operate only on provided target content and supplied skill context.
- Preserve/produce valid Org structure.
- Return artifact-only Org output; no commentary, no markdown fences.
- Respect skill contracts/requirements when present.
- Do not invent missing context outside provided input.

Prompt-quality guardrails:
- Explicitly require heading-consistent Org output.
- Explicitly disallow meta-text such as “Here is the rewrite...”.
- Emphasize deterministic transformation over creative expansion.

** 5) Dispatch Integration
Route per role at one central dispatch point:
- Derive effective model from request role + role-specific defcustom.
- Derive effective system prompt from request role + role-specific defcustom.
- Call `gptel-request` with both prompt body and role-scoped system/model options.

Compatibility rule:
- If model is nil, omit explicit model argument and let gptel default apply.
- If system prompt is empty string, fallback to default role template to avoid unguarded dispatch.

** 6) Validation and Errors
- Unknown role should signal explicit `org-ai-skills-gptel-error`.
- Non-string system prompt values should be rejected by defcustom type.
- Planner parser remains strict even if model/system are customized.

** 7) Observability
Extend debug entry fields with:
- `request-role`
- `effective-model`
- `effective-system-prompt-fingerprint` (or truncated preview; avoid full log spam)

This keeps routing auditable without leaking very large prompt text repeatedly.

* Acceptance Scenarios
1. Planner role uses planner model
- Given `org-ai-skills-model-planner` is set and execution model differs,
  planner dispatch uses planner model.

2. Execution role uses execution model
- Given planner and execution models differ,
  rewrite/step dispatch uses execution model.

3. Nil model fallback
- Given role model is nil,
  dispatch falls back to gptel default model without error.

4. System prompt routing
- Planner and execution requests carry different system prompts as configured.

5. Contract stability
- Planner still rejects non-JSON or invalid-skill plans regardless of model/prompt overrides.
