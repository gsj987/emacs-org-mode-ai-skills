#+TITLE: PRD 023 - Call-level watchdog and API-call DAG visibility
#+STARTUP: overview

* Problem
Current execution timeout is enforced at step lifecycle level, not per underlying API call. A single long step with many tool-call/tool-result rounds can time out even when progress is ongoing. Also, DAG visibility is currently step-centric, which makes it hard to inspect detailed cost/latency per API call within a step.
In practice, this creates false timeouts for steps that are actively making progress through many tool calls.

* Scope
- In scope:
  - Redefine watchdog semantics from per-step timeout to per-API-call timeout for planner and execution requests.
  - Ensure long multi-call steps can continue as long as each individual API call completes within timeout.
  - Treat timeout as an inactivity watchdog, not a cumulative step wall-clock limit.
  - Reset watchdog window when a new tool call is issued (or equivalent call-progress event is observed) within the same step.
  - Extend run-state observability so each API call is represented under its parent step in DAG rendering.
  - Add per-tool-invocation timing events so tool latency is visible separately from total execution API-call duration.
  - Include per-call timing and usage/cost fields where provider data is available.
  - Add ERT coverage for watchdog semantics and call-level DAG event recording.
  - Add/update BDD scenario(s) validating non-hanging behavior and detailed DAG visibility.
- Out of scope:
  - Changing skill selection logic or planner JSON contract.
  - Provider-specific billing normalization changes beyond current usage extraction pipeline.
  - UI redesign outside required DAG information additions.

* Constraints
- Technical constraints:
  - No fallback logic; failures must be explicit and root-cause preserving.
  - Keep existing fail-fast behavior for terminal-empty payloads and tool errors.
  - Maintain compatibility with current planner/execution callback event shapes.
  - Preserve existing top-level step status transitions (`running -> success/error/canceled`).
  - Do not enforce an additional cumulative per-step timeout when call-level progress is ongoing.
- Process constraints:
  - PRD-first implementation only.
  - Add tests in =tests/org-ai-skills-test.el= and BDD under =tests/bdd/=.
  - Update =README.org= for timeout semantics and DAG observability changes.

* Expected Behavior
- Behavior 1:
  - A long task with multiple API calls inside one step does not fail due to cumulative step duration alone.
  - Timeout is evaluated as a call-level inactivity window, not as total elapsed step time.
- Behavior 2:
  - If one API call exceeds timeout without terminal callback or progress signal, runtime fails that call explicitly and surfaces failure in run-state.
- Behavior 3:
  - When a tool call is emitted and execution continues, watchdog timing is reset/advanced to the new call boundary so active multi-call chains are not timed out.
- Behavior 4:
  - DAG output includes call-level nodes/events nested under each step with:
    - call id/index
    - request role (planner/execution)
    - duration
    - usage/cost (when present)
    - status (success/error/timeout)
- Behavior 5:
  - DAG output includes tool-level timing nodes/events (for example =tool.call:search1api...=) distinct from =api.call= and =execution.step=.
  - Tool-level duration reflects tool invocation lifecycle, not total step duration.
- Behavior 6:
  - Tool timing pairing remains stable when async callbacks reorder/reshape tool arg payloads between =tool-call= and =tool-result=.
- Behavior 7:
  - Existing planner and execution regression tests remain passing.
- Behavior 8:
  - DAG text view shows dependency levels with visible indentation so parent/child layering is easier to scan.
  - Indentation can return to shallower levels between independent/sibling branches.

* Open Questions
- Should per-call timeout reuse existing variables (=org-ai-skills-planner-request-timeout-seconds= and =org-ai-skills-execution-request-timeout-seconds=) with clarified semantics, or introduce new variable names and deprecate old ones?
- For DAG presentation, should call-level nodes be always-on or gated by observability level?
- Which callback event(s) are authoritative for "watchdog reset" (tool-call emission only, or any non-terminal progress event)?
