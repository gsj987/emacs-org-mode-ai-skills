#+TITLE: PRD 023 - Call-level watchdog and API-call DAG visibility
#+STARTUP: overview

* Problem
Current execution timeout is enforced at step lifecycle level, not per underlying API call. A single long step with many tool-call/tool-result rounds can time out even when progress is ongoing. Also, DAG visibility is currently step-centric, which makes it hard to inspect detailed cost/latency per API call within a step.

* Scope
- In scope:
  - Redefine watchdog semantics from per-step timeout to per-API-call timeout for planner and execution requests.
  - Ensure long multi-call steps can continue as long as each individual API call completes within timeout.
  - Extend run-state observability so each API call is represented under its parent step in DAG rendering.
  - Include per-call timing and usage/cost fields where provider data is available.
  - Add ERT coverage for watchdog semantics and call-level DAG event recording.
  - Add/update BDD scenario(s) validating non-hanging behavior and detailed DAG visibility.
- Out of scope:
  - Changing skill selection logic or planner JSON contract.
  - Provider-specific billing normalization changes beyond current usage extraction pipeline.
  - UI redesign outside required DAG information additions.

* Constraints
- Technical constraints:
  - No fallback logic; failures must be explicit and root-cause preserving.
  - Keep existing fail-fast behavior for terminal-empty payloads and tool errors.
  - Maintain compatibility with current planner/execution callback event shapes.
  - Preserve existing top-level step status transitions (`running -> success/error/canceled`).
- Process constraints:
  - PRD-first implementation only.
  - Add tests in =tests/org-ai-skills-test.el= and BDD under =tests/bdd/=.
  - Update =README.org= for timeout semantics and DAG observability changes.

* Expected Behavior
- Behavior 1:
  - A long task with multiple API calls inside one step does not fail due to cumulative step duration alone.
  - Timeout is evaluated per dispatched API call window.
- Behavior 2:
  - If one API call exceeds timeout without terminal callback, runtime fails that call explicitly and surfaces failure in run-state.
- Behavior 3:
  - DAG output includes call-level nodes/events nested under each step with:
    - call id/index
    - request role (planner/execution)
    - duration
    - usage/cost (when present)
    - status (success/error/timeout)
- Behavior 4:
  - Existing planner and execution regression tests remain passing.
