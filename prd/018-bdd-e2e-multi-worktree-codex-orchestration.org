#+TITLE: PRD 018 - Behavior-Driven E2E Testing via Multi-Worktree Codex Orchestration
#+STARTUP: overview

* Problem
Current testing is mostly ERT unit-level because plugin behavior depends on a personal Emacs runtime (=~/.emacs.d/init.el=), real gptel provider setup, and live API keys. This blocks reproducible end-to-end validation of user-observable behavior and prevents safe parallel feature verification with multiple Codex instances.

* Scope
- In scope:
  - Define a behavior-driven test specification format in natural language (user behavior + expected outcomes) for org-ai-skills.
  - Add a reproducible E2E test harness that runs Emacs with isolated test config (no dependence on personal init or secrets).
  - Support multi-worktree execution where each worktree can be driven by a dedicated Codex instance against a branch-scoped PRD.
  - Add orchestration entry points (scripts/commands) to create worktrees, assign scenario sets, run E2E suites, and collect results.
  - Provide deterministic provider simulation/stubbing for gptel interactions in E2E mode.
  - Define result artifacts for each run (logs, scenario pass/fail, traces) for auditability.
- Out of scope:
  - Replacing existing ERT unit tests.
  - Running real paid provider calls in CI by default.
  - Full distributed scheduler for remote machines.

* Ownership Boundary
- Primary ownership area for this PR:
  - =prd/018-bdd-e2e-multi-worktree-codex-orchestration.org=
  - =elisp/= (E2E harness integration points)
  - =tests/= (BDD/E2E coverage)
  - =scripts/= (worktree and E2E orchestration helpers)
  - =README.org= (usage updates)
- Expected conflict points:
  - Core execution APIs in =elisp/org-ai-skills.el= if concurrent feature branches also touch runtime orchestration.

* Constraints
- Technical constraints:
  - E2E mode must run with explicit isolated init (e.g. =emacs -Q= + controlled load path or dedicated minimal init file).
  - No runtime dependency on user secrets. Tests must pass with fake/mock providers.
  - Scenario execution must be deterministic enough for repeated local and CI runs.
  - Parallel worktrees must not share mutable runtime state (temp files, caches, sockets) unless namespaced.
  - Behavior specs must be machine-runnable while remaining human-readable.
- Process constraints:
  - PRD-first: implementation starts only after this PRD is approved/updated.
  - New behavior requires ERT/E2E tests, including failure scenarios.
  - README must document how to run BDD and E2E flows locally.

* Expected Behavior
- Behavior 1:
  - A developer writes a behavior scenario in natural language with explicit Given/When/Then expectations.
- Behavior 2:
  - Running the E2E command executes scenarios in an isolated Emacs runtime without loading personal =~/.emacs.d/init.el=.
- Behavior 3:
  - gptel/provider interactions are simulated or fixture-driven in E2E mode, so no real API key is required.
- Behavior 4:
  - Multiple worktrees can run independent scenario subsets in parallel, each with isolated artifacts and clear pass/fail summary.
- Behavior 5:
  - Failures include actionable traces (step, assertion, captured outputs, and relevant buffer/file state).

* Open Questions
- Should behavior scenario files live under =tests/bdd/= or =skills/...= with metadata tags?
  - Decision: all behavior scenario files live under =tests/bdd/= as org files.
- Preferred orchestration command surface:
  - one command for full flow (=create worktrees + run + aggregate=), or
  - separated commands for explicit control?
  - Decision: no extra orchestration command surface in first phase; focus on scenario-driven test cases defined in org files.
- Do we require optional “live provider” E2E profile for manual pre-release validation?
  - Decision: no live-provider profile in phase 1. Add dedicated E2E profile config (smaller model, think disabled) for faster and cheaper runs when provider-backed tests are enabled later.

* Agreed Decisions (Locked)
- BDD specs are org files under =tests/bdd/=.
- E2E v1 is scenario-first, no separate multi-command orchestration UX.
- E2E runtime has its own config profile, independent from user init.
- Phase 1 avoids live-provider dependency; provider behavior is deterministic via stubs/fixtures.

* Preview: E2E Test Script (=tests/e2e/org-ai-skills-e2e-test.el=)
#+begin_src emacs-lisp
;;; org-ai-skills-e2e-test.el --- E2E tests for org-ai-skills -*- lexical-binding: t; -*-

(require 'ert)
(require 'org)
(require 'org-ai-skills)

(defvar org-ai-skills-e2e-profile
  '(:model "gpt-4o-mini"
    :think nil
    :provider-mode stub)
  "Dedicated E2E profile. Must not depend on user init/secrets.")

(defun org-ai-skills-e2e--with-isolated-runtime (fn)
  "Run FN in isolated temp state for deterministic E2E behavior."
  (let* ((tmp (make-temp-file "org-ai-skills-e2e-" t))
         (user-emacs-directory tmp)
         (org-ai-skills-artifact-dir (expand-file-name "artifacts" tmp)))
    (unwind-protect
        (funcall fn)
      (delete-directory tmp t))))

(defun org-ai-skills-e2e--run-bdd-file (bdd-file)
  "Parse and run one BDD org file. Return plist result."
  ;; Preview contract only:
  ;; (:name "BDD 001" :status pass|fail :assertions (...) :artifacts (...))
  (org-ai-skills-bdd-run-file bdd-file org-ai-skills-e2e-profile))

(ert-deftest org-ai-skills-e2e-bdd-001-rewrite-subtree ()
  "End-to-end scenario: rewrite subtree with preserved heading."
  (org-ai-skills-e2e--with-isolated-runtime
   (lambda ()
     (let* ((result (org-ai-skills-e2e--run-bdd-file
                     "tests/bdd/001-rewrite-subtree.org"))
            (status (plist-get result :status)))
       (should (eq status 'pass))
       (should (member "heading-preserved" (plist-get result :assertions)))
       (should (member "body-updated" (plist-get result :assertions)))))))
#+end_src
