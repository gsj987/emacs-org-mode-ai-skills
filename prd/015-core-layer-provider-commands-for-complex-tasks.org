#+TITLE: PRD 015 - Core Layer Provider Commands for Complex Tasks
#+STARTUP: overview

* Problem
The system lacks a clearly defined core command layer that exposes essential runtime abilities to the LLM in a safe, composable way. Without this layer, complex tasks (such as learning an unfamiliar Python codebase and running guided experiments) become brittle, ad-hoc, and hard to test or reproduce.

* Scope
- In scope:
  - Define a core command catalog for essential operations needed by complex task execution:
    - Read/list/search files in a project.
    - Execute shell commands with explicit boundaries.
    - Execute Python snippets for rapid experiments.
    - Execute Org Babel code blocks as part of reproducible workflows.
  - Add a provider abstraction that maps command intents to Emacs implementations.
  - Add a minimal execution policy using:
    - Allowed command types list
    - Allowed folder/path scope list
  - Keep a simple structured result schema shared by commands.
  - Support command composition to enable multi-step higher-level tasks (explore -> inspect key functions -> run experiments -> summarize results).
  - Produce org-friendly outputs so the full exploration/experiment flow can be preserved as an Org document.
  - Keep interaction model fixed to existing org-mode workflow (no new interaction channels in this phase).
  - Reference Efrit-style usage patterns (tool-driven codebase exploration + iterative experiments) as design input, while adapting to this project's governance model.
- Out of scope:
  - Unbounded/arbitrary shell execution outside the allowed command and folder lists.
  - Domain-specific skill logic outside the core command layer.
  - Replacing existing skill governance flows.
  - Full autonomous software engineering loops (this PRD focuses on foundational command primitives only).
  - New UI/agent interaction paradigms beyond current org-mode usage.

* Constraints
- Technical constraints:
  - Commands must be deterministic/testable with clear input/output contracts.
  - Avoid hidden global state mutation; side effects must be explicit.
  - Must support future provider extensions without breaking compatibility.
  - Command execution results must capture enough metadata for reproducibility (command, cwd/context, exit status, stdout/stderr, timestamps when applicable).
  - Keep phase-1 safety checks minimal: enforce only command-type allowlist and folder/path allowlist.
- Process constraints:
  - No behavior changes without ERT coverage.
  - Any breaking contract proposal must be documented before implementation.
  - Design choices influenced by external systems (e.g., Efrit) must be translated into local constraints and tests, not copied implicitly.

* Expected Behavior
- Behavior 1:
  - LLM-facing core commands expose stable interfaces for file exploration and inspection (list/read/search) in a codebase.
- Behavior 2:
  - Every command returns normalized success/error payloads with actionable diagnostics.
- Behavior 3:
  - Before execution, runtime validates only:
    - command is in allowed command set
    - target folder/path is in allowed scope
- Behavior 4:
  - Complex tasks can chain core commands with predictable intermediate state.
- Behavior 5:
  - The user can prompt the agent to inspect a random Python repository, identify key functions/modules, run targeted shell/Python/Org-Babel experiments, and collect outputs into an Org document artifact.
- Behavior 6:
  - Failed command execution surfaces actionable failure details (validation error vs execution error) without silent fallback.
- Behavior 7:
  - All scenarios run from org-mode files using existing project workflow; no alternate interaction mode is introduced in this phase.
