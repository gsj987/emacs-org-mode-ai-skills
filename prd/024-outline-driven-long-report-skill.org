#+TITLE: PRD 024 - Outline-driven long report generation skill
#+STARTUP: overview

* Problem
Long report generation from large code/context sources can trigger broad exploration and unstable runtime behavior when one step attempts to draft the whole report. The system needs a dedicated skill workflow that expands a pre-existing outline incrementally (headline by headline) to improve controllability, quality, and runtime predictability.

* Scope
- In scope:
  - Add a new skill spec in =skills/= for long report generation from an existing outline.
  - Define explicit contracts requiring section-by-section expansion aligned to outline headlines.
  - Ensure planner can organize execution as headline-scoped steps (not one monolithic compose pass).
  - Provide tool-call guidance for bounded source reading per section (targeted file reads over broad traversal).
  - Add ERT coverage for skill parsing/invocation contracts and planner-step normalization constraints related to this workflow.
  - Add BDD scenario(s) for outline-to-long-report execution path.
  - Update README usage examples for this new skill workflow.
- Out of scope:
  - Automatic outline generation quality improvements (handled by other skills/PRDs).
  - Cross-document citation engine or external bibliography features.
  - New provider integrations.

* Constraints
- Technical constraints:
  - No fallback behavior; if section context is insufficient, fail explicitly or request replan via existing marker contract.
  - Preserve Org structure validity and heading hierarchy.
  - Keep generated output in original task language unless explicitly instructed otherwise.
  - Avoid unbounded repo scanning by contract; prefer section-scoped reading.
- Process constraints:
  - PRD-first implementation.
  - Add tests to =tests/org-ai-skills-test.el= and =tests/bdd/=.
  - Update =README.org= behavior and usage docs when feature lands.

* Expected Behavior
- Behavior 1:
  - Given an existing outline subtree, runtime generates a complete long report by expanding content under each headline in sequence.
- Behavior 2:
  - Planner produces multiple bounded steps (headline/section granularity) rather than one oversized compose step when this skill/workflow is selected.
- Behavior 3:
  - Each step output is structurally compatible with downstream merge/apply logic (valid Org subtree text only).
- Behavior 4:
  - Runtime observability shows progression by section so users can identify which section consumed time/cost.

- [X] Define planner-facing guidance so section/headline-level decomposition is preferred for this workflow.
- [X] Add ERT tests for skill metadata parsing, request composition expectations, and plan normalization constraints.
- [X] Add BDD scenario(s) for end-to-end outline-to-long-report flow and core assertions.
- [X] Update README with usage instructions and recommended planner settings for long reports.
- [X] Tighten skill output-format contract to require Org-only artifact text (no Markdown output/fences).

* Open Questions
- Should planner decomposition be enforced strictly by parser/runtime rule for this skill, or kept as prompt-level guidance first?
- Should section expansion order always follow outline order, or allow planner to reorder for dependency reasons?

* Decisions
- Planner decomposition for this workflow is prompt-level guidance first, with strict runtime output constraints reused from outline-compose (headline lock + property drawer omission).
- Section expansion order follows outline order by default for deterministic report flow.
- Planner decomposition is now runtime-enforced for matched outline-long-report intents: one heading section per step using =outline-driven-long-report=, with replan continuing remaining headings.
